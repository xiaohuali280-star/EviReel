# 笔记生成失败：排查与修复（2026-10-20）

## 实际原因

真实模型请求暴露了两层故障，原界面都只显示“笔记生成失败”：

1. **等待整段响应时连接中断**：原实现使用非流式请求，本地任务约 53 秒后收到 `RemoteProtocolError`。此前将单次等待从 60 秒改为 180 秒，仍不能解决对端提前断开。保持相同接口、模型、文稿和系统代理，流式请求能完整返回；一次真实调用约 6 秒开始收到内容，105 秒完成。证据支持采用流式传输，不能据此断言故障一定由代理或服务商中的哪一方引起。
2. **模型漏引材料**：完整返回后，模型生成 6 个章节，但只覆盖 18 个文稿来源中的 17 个；既有完整性校验正确拒绝了这份结果。扩大超时不能解决来源遗漏。

旧进程没有重载修改后的密钥也曾导致鉴权失败；这次验证前已确认当前密钥可用。界面的“已配置模型”仅表示存在配置，不代表鉴权或额度验证成功。

## 修复

- 新增 `vam/study_model.py`，默认使用 OpenAI 兼容流式响应，按 SSE 事件组装正文，处理 UTF-8/网络分片、心跳和 usage 事件。
- 必须正常结束且通过结构、来源身份和覆盖校验，才能发布成品。截断、过滤、异常 EOF、超长或非法输出均失败；局部输出不会保存为成功笔记。
- 每次模型调用默认等待 180 秒；网络/超时和特定临时 HTTP 状态默认最多调用两次。重试丢弃前一次的局部内容，正常关闭连接；取消不重试。
- 若首轮仅遗漏部分来源，额外调用一次模型，仅处理遗漏材料。补全仍须通过同样校验；再次遗漏或引用越界则整个任务失败，保留旧成品。没有放宽完整性检查，也没有用原文拼接冒充生成成功。
- 失败状态区分鉴权、模型不可用、限流、请求拒绝、连接中断、响应不完整、格式/引用错误和超时。接口与日志只使用固定错误分类，不公开服务商原始错误正文、密钥或文稿。
- 本地系统代理保持不变。构建后的网页资源同步更新，安装包与开发页面显示相同错误提示。

流式接入参考[硅基流动官方说明](https://docs.siliconflow.cn/docs/userguide/capabilities/stream-mode)。

## 配置与操作

在服务器 `.env` 中设置：

```dotenv
STUDY_MODEL_TIMEOUT_S=180
STUDY_STREAM=true
STUDY_MODEL_ATTEMPTS=2
STUDY_TIMEOUT_S=600
```

已有 `.env` 的显式旧值会覆盖程序默认值。修改后重启后端，再点击重新生成；刷新页面不会重跑已持久化的失败任务。服务商不支持流式时可设置 `STUDY_STREAM=false`，但仍需解决长响应被中断的问题。

单次等待覆盖完整请求，包含连接和读取；总任务仍受 `STUDY_TIMEOUT_S` 约束。补全最多新增一次生成，每次生成又受有界重试限制，可能增加模型用量。较长视频超时可调小 `STUDY_BATCH_CHARS`，同时核对完整批次数预算；不要通过跳过文稿解决失败。

| 页面提示 | 处理方法 |
| --- | --- |
| 密钥无效或没有权限 | 核对密钥、接口及模型权限，更新后重启后端 |
| 模型不可用 | 核对模型完整名称，或等待服务恢复 |
| 额度不足/请求频繁 | 检查余额和调用限额，稍后重试 |
| 连接中断 | 检查网络、代理和服务状态；默认流式及有界重试已启用 |
| 响应不完整/格式或引用失败 | 重试，必要时减小批次；失败成品不会覆盖原有笔记 |

## 验证结果

先写回归测试并确认旧实现失败：非流式连接中断，以及遗漏来源无法定向补全。修复后：

- 完整 Python 测试：**201 passed**；笔记与 HTTP 专项：**28 passed**。
- 前端契约：**3 passed**；类型检查、生产构建通过。
- 经用户明确授权，使用已配置的硅基流动接口和原有真实视频文稿执行完整持久任务：**succeeded，约 117.45 秒，5 个章节，18/18 来源覆盖，无旧版标记**。此为真实模型验收，不是 Mock。
- 同一真实成品的 Markdown、PDF、PPTX 导出均返回 HTTP 200，文件分别为 6,194、11,955、40,466 字节；检查了 `%PDF`/ZIP 文件签名。
- 自动测试使用明确模拟模型，覆盖连接失败重试、分片、截断、取消清理、错误脱敏、补全上限、旧成品保留及事务发布。来源覆盖不等同于笔记事实完全正确，文稿仍可能有 ASR 误差。
