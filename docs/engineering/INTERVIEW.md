# EviReel 面试材料

规则：每个数字都标出处；没测过的不写数字。三类状态分开说：**已实现并验证**（有测试或报告）、**已实现待验证**（代码在，缺真实条件）、**设计中/未做**。

## 两分钟项目介绍

EviReel 是一个课程视频学习工具：上传视频后自动转写字幕、抽取画面，用户可以就视频提问，回答都带可点击跳转的时间点证据，还能生成笔记和课件。我在已有产品功能之上做了四个阶段的后端工程化：

- **E1 可续传上传**：大文件分片直传对象存储，PostgreSQL 记账。断网、刷新后只补传缺失分片，并在续传前核对已传分片的内容，避免把两份文件的分片拼在一起。
- **E2 可靠异步处理**：把转写、抽帧、向量化放进 RabbitMQ + Celery 的独立 Worker。任务受理和派发用 Outbox 写在同一个事务里；阶段带租约和 attempt token，被 kill -9 的 Worker 由别人接手，旧执行者不能覆盖新结果。
- **E3 并发与多实例**：先压测出瓶颈是每个视频一把锁，改成版本快照加跨实例读租约。同一视频 20 并发时，P95 从 17.9 秒降到 2.4 秒（本机单实例压测，模型调用由模拟器代替，不是真实供应商的延迟）。在此基础上做了两个 API 实例、Redis 全局模型限流和 PostgreSQL 用量账本。
- **E4 评测与检索**：建了一套可重跑的评测工具（题集格式、指标、运行器，真实运行复用 E3 的租约、限流和用量账本），加了关键词检索通道、“低成本 / 深度 / 自动”三种回答路径，以及多轮 Agent 的对照入口。真实效果评测还没做，原因是缺少有授权的视频、人工标注和模型预算。

E1–E4 都通过了独立验收；E4 通过的范围是评测工具、合成验证和工程交付，真实效果评测还没做。E4 共三轮验收，前两轮发现 4 个问题（real 评测绕过平台保护、Agent 对照未实现、视觉检查失败仍标 answered、并行调用突破评测预算）。验收发现的问题都是先写出能复现的测试再修。

数字出处：`docs/engineering/E3_DELIVERY.md` 第 8 节（本机单实例、模型模拟器、关缓存）。

## 三个核心技术难点

### 1. 续传时怎么保证最终文件就是用户选的那个文件（E1，已实现并验证）

- **问题**：分片直传后，服务端只看到对象存储里的分片。用户刷新后可能重新选错文件，网络异常时“合并成功但数据库没记上”的窗口也会存在。
- **做法**：
  - PostgreSQL 记录上传会话和分片账本，以对象存储的 ListParts 为准对账；
  - 续传前，前端在 Web Worker 里对重选文件逐片计算 MD5，与存储确认过的分片 MD5 比对，不一致就拒绝，一个字节也不发；
  - 合并和验证分开，验证阶段服务端流式计算 SHA-256，并核对 S3 复合 ETag；
  - 状态转换都是带当前状态条件的 UPDATE；配额在会话创建时于行锁下预占。
- **验证**：真实 PostgreSQL + MinIO 的平台测试（`tests/test_e1_platform.py`）覆盖续传只补缺失分片、合并成功但 DB 失败后对账恢复、取消与完成竞争只有一个赢家等场景；还有浏览器续传用例 2/2。见 `E1_DELIVERY.md` 第 6 节。

**常见追问**
- *为什么不用整文件 MD5？* 浏览器端算整文件哈希要读完全部字节，续传时代价太大。分片 MD5 既是 S3 的签名内容，也足以做内容一致性核对。
- *复合 ETag 能证明什么？* 只能证明组装的是签过名的那些分片，不能证明分片来自同一个文件，所以另有前端逐片核对。

### 2. Worker 随时可能被 kill，怎么做到不丢、不重复发布（E2，已实现并验证）

- **问题**：长任务（转写、抽帧）中途进程被杀、消息重复投递、旧执行者“复活”后提交过期结果。
- **做法**：
  - 任务、阶段和 Outbox 行在同一个 PostgreSQL 事务里写入，由派发器投递到 RabbitMQ；
  - 每次执行都认领一个带租约的 attempt token，提交时检查 token，过期 token 的提交被拒绝；
  - ASR 结果和 Embedding 批次作为检查点存进对象存储，并校验 sha256，重试时复用；
  - 发布是“先决定（写账本）、再投影（写读模型）”，按任务序号 fence，旧任务不能覆盖新发布。
- **验证**：Linux CI 上 14 个故障测试，用真实 RabbitMQ 和独立 Worker 进程，包括 kill -9、broker 停启、重复消息、旧 Worker 复活。见 `E2_DELIVERY.md` 和 `STATUS.md`。

**常见追问**
- *这是 exactly-once 吗？* 不是。消息至少投递一次，靠账本条件提交和幂等投影让结果收敛；外部模型调用本身也可能重复，所以不宣称严格一次。
- *为什么不直接用 Celery 的重试？* Celery 只管消息，不知道业务阶段和检查点；租约和 attempt token 让“谁有权提交”由数据库决定。

### 3. 多人同时问同一个视频，怎么既快又不读到被删掉的文件（E3，已实现并验证）

- **问题**：基线中每个视频一把锁，同一视频 20 并发时吞吐只有 1.2 次/秒；状态（读者计数、锁、任务）都在进程内存里，不能开第二个 API 实例。
- **做法**：
  - 去掉锁；每个请求先取得写明所读版本的读租约，再从这些版本生成快照；
  - 租约、删除标记、旧版本回收在 PostgreSQL 里，用同一把按视频划分的 advisory lock 串起来；
  - 回收分“认领”（拒绝新读者）和“清理完成”两步，失败可重试；
  - 模型调用统一走 ModelGateway：Redis Lua 原子地做全局限流和在途槽位，PostgreSQL 记预占和结算；
  - Redis 不可用时直接拒绝，不退化成各实例各自放行。
- **结果**：同一视频 20 并发，P95 17.9 秒 → 2.4 秒；固定每秒 5 个请求时，P99 64 秒 → 0.32 秒（本机单实例、模型模拟器、关缓存，`E3_DELIVERY.md` 第 8 节）。三轮独立验收发现并修复了 5 个竞争或恢复缺陷，例如“快照和租约之间的空档”“租约过期后读取仍在继续”，都先写了能确定性复现的测试。

**常见追问**
- *为什么租约放 PostgreSQL 不放 Redis？* 租约决定文件能不能删，属于正确性，要和删除标记、任务插入在同一个事务里判断；Redis 只放丢了也能重建的东西。
- *两个实例的吞吐提升了多少？* 没测。只验证了两个实例的正确性（CI 容器冒烟：停掉一个 API 后 20/20 请求成功）。压测数字是单实例的。

## 关于 E4（如实说）

- **验收结论**：工具与合成验证交付已通过第三轮验收；真实效果验证待补齐。
- **已实现并验证（模拟器 + 单元测试）**：
  - 评测题集格式（类别、调参集与保留集、标签来源）；
  - 指标定义和分母：证据 Recall@K、MRR、自动引用支持率、时间定位误差、无答案拒答率、延迟、调用数、token，无法计算的项明确标出；
  - 可重跑的运行器和元数据；
  - 关键词通道：中文按两字切分，代码符号保留完整写法并拆成各部分；
  - 回答路由：明确规则、一次有界的升级、规则拒答，并记录 status 和 route；需看画面的问题只有在画面真的被读到、且引用了读到的证据时才算 answered（首轮验收发现的缺陷，已补回归测试）；
  - 多轮 Agent 对照：接入产品现有的工具调用循环，轮次、候选、截止时间和预算都有上限，用可控替身测过超时、预算耗尽和异常；
  - 真实运行的装配：与 API 共用读租约、Redis 限流、PostgreSQL 用量账本和工作区预算，评测只在其上叠加逐题归属和本轮上限（用真实 PostgreSQL 测过，没有调用付费模型）；
  - 本轮上限在并发下成立：检查和占用在一把锁里完成，平台预占阻塞、拒绝、异常、取消时归还额度（第二轮验收发现的并发漏洞，已补回归）。
- **已实现待验证**：这些机制在真实模型和真实视频上的效果。合成题集 + 模拟器的数字只能证明工具和逻辑正确，不能说成“准确率提升 X%”或“成本降低 X 元”。
- **待补齐**：真实视频、人工标签、真实模型效果、实际费用和延迟、人工引用审核。
- **未做（按条件不需要或可选）**：向量索引（按实测判断不需要，理由见 `E4_DELIVERY.md`）、跨视频检索。
