# E3 交付：并发、资源隔离与多用户保护

状态：**第二轮验收的 1 项问题（P2，旧代次清理无法重试）已整改，待复验**（不是验收通过）。代码提交与 CI 结果见 `STATUS.md`。

范围：两个 API 实例 + 独立 Worker 共享 PostgreSQL / RabbitMQ / Redis / 对象存储；热门视频并发读取；多用户隔离；所有实例共用的模型配额。E2 的持久受理、Outbox、条件提交、检查点和清理协议原样复用，Redis 不承载任何业务账本。

## 1. 状态归属

| 数据 / 状态 | 权威存储 | 合法写入者 | 并发保护 | 恢复方式 |
| --- | --- | --- | --- | --- |
| 任务与阶段（jobs / job_stages / outbox） | PostgreSQL（E2） | API 受理；Worker 按 attempt token 提交 | 条件更新 + 唯一约束 + 任务序号 fence | 扫描器重新派发过期租约（E2） |

| 读者租约 `read_leases` | PostgreSQL | 读取中的实例（检索、播放、导出、问答） | 与删除共用每个视频的 advisory lock（7032） | 实例崩溃后租约过期，不再保护文件 |
| 删除标记 `video_tombstones` / 退役代次 `retired_generations` | PostgreSQL | 删除请求、`project` 阶段 | 同上；与任务插入互斥 | 任一实例的清扫器完成回收 |
| 问答请求归属（owner + lease_until） | registry `conversation_requests` | 受理问答的实例 | 写事务内检查视频状态、单会话一个活动请求、全局容量 | 心跳续租；租约过期后由任一实例标记 interrupted |
| 上传会话与验证 | PostgreSQL（E1） | 认领验证租约的实例 | `state_version` 认领令牌 + 租约 | 对账器重新驱动过期租约（E1） |
| 模型用量 `model_usage` / 预算 `model_budgets` | PostgreSQL | ModelGateway | 每个空间的 advisory lock（7033） | 过期预占转为 unknown，按估算继续计入 |

## 2. 版本快照与删除协议

- **快照**：`IndexingService._pin` 先读视频行并取得租约（租约写明该行的视觉代次和字幕文件），再从这些代次生成 `ReadSnapshot`（文本/检索版本、Embedding 身份）。协调器在每个视频的 advisory lock 下授予租约：若租约所列代次已被认领删除，则拒绝（`snapshot_stale`），调用方重新读取视频行并重新固定，最多重试 5 次。因此请求持有的租约一定指向尚未删除的代次，读取文件都在取得租约之后。问答各步、来源引用、查询向量缓存键和派生摘要都使用同一快照。新版本发布后，已开始的请求继续读旧代次。字幕上下文、帧记忆、笔记语料和导出使用同一取租约方式（第一轮验收 P1-1）。
- **发布与退役**：`project` 阶段先把旧代次记入 `retired_generations`，再条件发布；旧代次的对象离开清单后进入 `object_deletions`（原因 `superseded`）。回收分两步，各自持久记录（第二轮验收 P2）：
  1. **认领**（`removed_at`）：清扫器拿到候选后，在每个视频的锁下执行 `claim_removal`。只有没有未过期租约指向该代次时才认领；认领后，指向它的新租约一律被拒绝（`snapshot_stale`）。在候选列表之后才写入的租约会让认领失败，文件保留。
  2. **清理完成**（`cleaned_at`）：认领提交后才删除文件。删除是幂等的：已不存在的文件视为成功，其他错误会上抛；确认没有残留后才记录 `cleaned_at`。
  - **失败或中断后的恢复**：删除失败（记录 `cleanup_attempts` / `cleanup_error`）或进程在认领后中断时，该代次保持“已认领、未清理”，仍是候选，也仍然拒绝读者。之后任一实例的清扫器再次调用 `claim_removal` 时会得到“可以继续删除”，于是接着清理。
  - **防止挤占**：每批候选中，待重试的最多占一半，按尝试次数排序，反复失败的清理不会挤掉新候选。
  - **并发清扫**：多个清扫器同时处理同一代次是安全的，删除与 `mark_cleaned` 都是幂等的。
  - **重新发布**：若该代次重新被发布且尚未认领，从退役表移除，不会删除。
  - **已删除视频**：回收时同样在删除文件前于锁下用 `claim_reclaim` 复核没有租约；失败时视频保持 `delete_failed`，清扫器会再次回收（原有行为）。
  - **本地协调器**：语义相同（已认领集合、已清理集合、失败计数）。
- **删除**：
  1. 一个 registry 写事务内检查活动任务、问答和笔记，并把视频标记为 `deleting`。受理问答、任务、笔记时也在各自的写事务里检查这一状态，因此检查与标记之间不能插入新工作。
  2. 在 PG 中写入删除标记。它与读者租约、流水线任务插入共用每个视频的 advisory lock：标记写入时若有活动任务，删除被拒绝；标记写入后，新任务和新读者都被拒绝。
  3. 有读者时返回 `202 deleting`；读者释放或租约过期后，任一实例的清扫器回收。回收顺序是：先把已发布对象登记为待删除，再删除 registry 行，最后释放所有权和配额。
- **租约丢失**（第一轮验收 P1-2）：
  - **本地有效期**：共享租约在本地记录截止时间 = 最近一次成功写入开始时刻 + TTL − TTL/6，并且不超过 `READ_LEASE_MAX_S`。数据库中的过期时间由服务端在这之后计算，所以本地有效期总是早于数据库行过期。
  - **续租**：只延长尚未过期的行（`expires_at > now()`），已过期或已消失的行不会被复活。
  - **判定为丢失**：达到最大寿命、续租失败且超过本地截止时间（独立的 0.5 s 检查，不受挂起的数据库调用影响），或行已过期。此时回调立即执行：受保护的检索、字幕、帧记忆和导出被取消，返回 `503 read_lease_lost`；正在流式发送的播放响应停止发送，连接被断开，播放器需用 Range 重新请求，届时会取得新租约（浏览器重连行为未实测）。
  - **丢失后的行**：不主动删除，等它自然过期，让已在线程中执行的读取在剩余 TTL 内结束，之后清扫器才可能删除文件。
  - **启动检查**：要求 `READ_LEASE_MAX_S ≥ CONVERSATION_REQUEST_TIMEOUT_S + READ_LEASE_TTL_S`，否则拒绝启动，保证问答在自身截止时间之前不会因租约寿命被取消。
  - **Worker**：读取已发布代次（笔记语料）时也持有真实的 PG 租约，由后台线程续租；不再依赖宽限期。
  - **实例崩溃**：其租约最多在一个 TTL 后过期。

## 3. ModelGateway

问答、视觉检查、Embedding、重排序和笔记生成的模型调用，包括重试，全部经过 `vam/gateway`。每次尝试的流程：

1. **准入**：在 Redis 中用一个 Lua 脚本检查全局 RPM、供应商 RPM、供应商 TPM（按估算 token）、空间 RPM，以及供应商、空间和离线在途槽位，全部有余量才一次性扣减。速率用滑动窗口计数（本分钟计数加上上一分钟按未过去比例折算）；时钟取 Redis `TIME`，与实例时钟无关。
2. **预占**：PG 中写入 `reserved` 行，在空间锁下检查每日 token 预算。
3. **调用**：每次尝试受超时限制，整个请求另有总截止时间。
4. **结算**：按供应商返回的用量记为 `settled`；确定未计费（发送前被拒、4xx）记为 `failed`；超时或断线后结果未知记为 `unknown`，按估算继续计入预算，不当作未消费。
5. **释放**：释放槽位；供应商实际 token 超出估算时，差额补记到 TPM 窗口。

- **重试**：429、5xx、超时和传输错误按指数退避加全抖动重试，遵守 `Retry-After`；每次尝试单独计费和计数。
- **槽位租约**：租约时长为单次超时加宽限期。调用本身受这个超时约束，持有者崩溃后槽位到期失效，不会出现租约过期后仍无约束运行的调用。
- **离线与交互分开**：离线（流水线、笔记）槽位上限小于供应商总上限，差额留给问答。笔记生成使用单独的 `notes` 队列和 Worker 池。
- **有界等待**（第一轮验收 P2-3）：一次请求的总截止时间是绝对时刻，同时约束准入等待、重试退避、预占和每次调用；过了截止时间不再准入，也不再调用供应商，返回 `504 model_deadline_exceeded`。准入等待预算（交互 `MODEL_QUEUE_WAIT_S`、离线 `MODEL_OFFLINE_QUEUE_WAIT_S`）由同一请求的所有尝试共用，重试不会重新获得完整预算。每个进程的等待者数量有上限，超出时立即返回 429。同步与异步两个入口共用同一套准入、预占、结算和重试步骤，只有休眠和调用方式不同。
- **故障策略**：

  | 故障 | 处理 |
  | --- | --- |
  | Redis 不可达 | 默认 `reject`：返回 503，不调用模型。`local`（进程内限流）只允许在唯一调用模型的进程中使用，即单个 API 且没有流水线 Worker。多实例或 worker 模式下，API 拒绝以 `local` 启动，Worker 忽略该设置并按 `reject` 处理（第一轮验收 P2-4）。本地限额不再向上取整：份额为 0 或限额为 0 都拒绝 |
  | RabbitMQ 不可达 | 沿用 E2：受理照常写入 Outbox，发布延后 |
  | 模型不可用 | 重试耗尽后，问答返回错误终态，流水线阶段按 E2 的退避重试 |

## 4. 授权、缓存与通知

- **授权**：视频、任务、会话、来源、笔记、导出、WebSocket 和播放 URL 都按所属空间检查。中间件先解析资源所属的视频，再核对视频所属空间（E1 机制）。E3 增加了两个用户、两个实例的整套 404 测试。
- **缓存**：只缓存查询向量。键包含所属空间（授权范围）、Embedding 模型身份、指令和查询文本。查询向量与来源版本无关，所以不含版本；候选结果和答案都不缓存。相同在途计算会合并：先到者持有带令牌的锁，写入前在 Lua 中比对令牌，锁已过期的旧执行者写不进去。失败结果不缓存；TTL 带 ±10% 抖动。
- **通知**：终态先写入请求行，再发布事件。Redis Pub/Sub 只用于跨实例实时推送；连在 B 上的客户端用同一 `request_id` 重发，就能订阅 A 上正在执行的请求。Pub/Sub 不保留历史，断线期间的中间进度会丢失，客户端以请求快照为准。不宣称支持事件重放。

## 5. 部署与运行

```bash
docker compose --env-file deploy/e1/dev.env -f deploy/e3/compose.yml up -d --build --wait
```

- **组成**：PostgreSQL、MinIO、RabbitMQ、Redis，`api-1` / `api-2` 经 nginx 轮询（无粘性会话）。dispatcher 负责发布，`worker-media`（media、asr）、`worker-embed`（embed、control）、`worker-notes`（notes）分开处理。
- **诊断**：每个响应带 `X-EviReel-Instance`；`/api/health` 返回实例 id；`/api/metrics` 提供网关、缓存、事件、读者和协调计数。
- **限制**：API 和 Worker 共享一个 DATA_ROOT 卷，因此是**单机部署**。索引代次虽然可以从对象存储重建，但字幕库文件会原地追加新版本：实例各用独立卷时，已存在的旧字幕文件不会被识别为过期。同机多进程的验证不代表任意多机部署能力。
- **本地**：本机（Windows）没有 Redis，conda-forge 不提供 Windows 版，WSL 不可用。因此真实 Redis 测试和容器栈只在 Linux CI 上运行；本机的 PG + MinIO 测试中，各实例使用进程内限流和缓存。

## 6. 迁移与回退

- **迁移**：
  - 平台 schema 升到 8：`007_e3_concurrency.sql` 新增租约、删除标记、退役代次、模型用量与预算表，并在删除原因约束中加入 `superseded`；`008_generation_cleanup.sql` 为退役代次增加 `cleaned_at`、`cleanup_attempts`、`cleanup_error`。迁移前已认领的代次视为未清理，会被重新执行一次（删除是幂等的）。
  - SQLite registry 升到 7：006 增加问答归属列，007 增加 `publication_objects`。
  - 切换到 PG 读模型：先停止写入，再执行 `python -m vam.storage.pg_registry copy --data-root DATA_ROOT --database-url URL`。该命令逐表复制，校验行数和内容摘要，目标非空时拒绝执行；然后设置 `REGISTRY_BACKEND=postgres`。
- **回退**：
  1. 停止写入，执行 `copy --to sqlite`，把 PG 读模型写回一个空的 SQLite 文件（同样校验），然后设置 `REGISTRY_BACKEND=sqlite`、`API_MULTI_INSTANCE=false`，只保留一个 API。
  2. 若要回退到 E3 首轮代码，删除 008 新增的三列、约束和索引，并删除 `schema_migrations` 中的版本 8。若要回退到 E2 代码，还需删除 007 新增的表，把删除原因约束改回 E2 的值，并删除版本 7。SQLite 需要删除 `publication_objects` 表和 006 新增的两列，并把 `user_version` 设回 5。
  3. 复制工具的往返已在真实 PG 上测试；完整的回退流程尚未在数据副本上演练。

  - 跨实例单飞，锁过期后的旧执行者不能覆盖新值；
  - Pub/Sub 跨实例投递；
  - 两实例多实例模式：A 上执行的问答由 B 上的 socket 实时跟随（真实 PG + S3 + Redis，问答模型为可控模拟器）。
- 产品回归：P1–P5 用例在 `REGISTRY_BACKEND=postgres` 下再跑一遍；E1/E2 用例在 schema 7 上回归。

## 8. 压测

脚本：`scripts/e3/bench_server.py`（真实 API 与真实 SQLite 索引；模型为固定延迟的**模拟器**，Embedding 40 ms、VLM 400 ms）、`loadgen.py`、`run_matrix.py`。数据规模：4 个视频，每个 300 帧（含 JPEG 载荷）、60 个事件、200 个字幕块，向量维度 1024。每个场景运行 20 s 并预热。结果 JSON 保存在 `docs/engineering/e3-bench/`，每份都附有代码版本、环境、配置和资源占用。

- **环境**：Windows 11，32 逻辑 CPU，Python 3.11.16，单个 API 进程，本机 PostgreSQL 16（仅用于 PG 读模型那一组）。
- **基线**：在隔离目录中用 `b39a564` 测量，当前工作区未回滚。
- **对照**：其余三组在提交 `2916817`（`git_dirty=false`）上测量。
- **压测方式**：走 HTTP 检索接口，每个请求调用三路检索（帧、事件、字幕）。WebSocket 连接数不等于模型并发。

解读：

- **基线瓶颈**：每个视频一把锁，请求排队；每个请求都重新加载索引；字幕检索是逐条的 Python 扫描。到达率为 5/s 时基线只能处理 1.2/s，P99 达到 64 s，队列一直在增长。E3 在这两个到达率下都跟得上。
- **热缓存**：压测脚本循环使用少量固定查询。热缓存组里所有查询向量都命中缓存，模拟器收到的 Embedding 调用为 0；低并发下省掉了 40 ms 的模型时间。无缓存组（`CACHE_ENABLED=false`）是冷路径。两组都如实列出，热缓存结果不代表真实查询分布。
- **高并发**：C≥10 时，两组都受 CPU 限制（约 1.6–1.9 核，事件循环 P95 延迟最高约 100 ms，最长的是字幕检索）。热缓存组在高并发下没有更快，个别场景还更慢；没有分析，原因待查，不作结论。
- **PG 读模型**：与 SQLite 相比，同视频 C=5–10 慢 10–20%，其余场景相近。这是本机 PG 的数字。

## 9. 容量边界与未验证项

- 单实例在 C≥10 时受 CPU/GIL 限制（约 1.6–1.9 核，同视频 C=20 时事件循环 P95 延迟约 100 ms，见第 8 节）。本机单实例在模拟器下约 10–15 次检索/秒，这是当前的容量边界，不代表线上数字。registry 和协调调用仍是同步 PG 调用，有一部分在事件循环上执行（已加连接池，单次约 1–2 ms），留给 E4 评估。
- 两实例的吞吐压测没有做：本机没有 Redis，而 CI 机器的环境与本机基线不可比。两实例只做了正确性验证。
- 本轮没有调用真实模型（没有授权预算）：ModelGateway 的计费数字来自模拟器和测试替身；供应商返回的真实 usage 字段格式在真实调用前尚未核对。
- 未验证：各实例使用独立 DATA_ROOT 卷的部署（受字幕文件原地追加限制）；多主机部署；Redis 主从切换；回退手册的完整演练。
